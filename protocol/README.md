# DRouter protocol v1

The device owns all state. `protocol.schema.json` defines each application request and its parameters. `generate.py` generates this schema and the TypeScript operation inventory; regenerate from the repository root with `python3 protocol/generate.py`. Rust deserialization and operation handlers enforce the same constraints, including unknown parameter rejection. Both local and remote requests reach `Device::frame` and `Device::execute`.

Application requests contain `v: 1`, a bounded string `id`, an allowlisted `op`, and object `params`. Responses contain the same `v` and `id`, `ok`, and either `result` or `error: {code,message}`. There is no arbitrary HTTP, URL, shell or subnet-scan operation. Wi-Fi profile responses contain ID, SSID, enabled state, and priority; passwords are omitted. `wifi.add` updates an existing ID and preserves a blank/omitted password. `wifi.set_enabled`, reorder, removal, and explicit connect use the same core locally/remotely. Changes that can break the active remote Wi-Fi link require `confirm_disconnect:true` when no wired recovery route exists. Settings updates require `expected_revision` to prevent overwriting another administrator's changes.

## Authentication and transport

The browser and device use the same RustCrypto `srp` 0.6 implementation, compiled to native Rust on the device and WebAssembly in the browser. Group: RFC 5054 2048-bit, SHA-256, SRP-6a, username `admin`. RustCrypto's documented proof convention is used unchanged by both endpoints. The password input is first hardened using PBKDF2-HMAC-SHA256, 100,000 iterations, a per-device 32-byte salt, and a 32-byte result. Passwords contain 4–128 Unicode scalar values; see the counting rule below. Only salt and SRP verifier reside on the device. Cloudflare receives neither password nor verifier.

The salt is SHA-256 of UTF-8 `drouter-srp-salt-v1:` followed by the device's 32-character public identity fingerprint. The identity contains 128 bits of cryptographic uniqueness. Legacy administrator credentials retain this public, device-specific salt across friendly-name changes. Password changes use a fresh random salt; the synthetic unavailable-device challenge retains the legacy derivation. An unavailable relay returns a synthetic challenge with the same salt derivation and random public ephemeral, then a generic failure. This avoids an explicit unknown-device response and a changing-salt existence oracle. Response timing is not claimed to be indistinguishable across arbitrary networks.

Local transport starts with `POST /session` returning a random 36-character session ID. Subsequent `POST /api` requests contain `{sid,frame}`. A local simulator WebSocket is also available at `/ws`; the ESP32 UI uses HTTP to limit resources. Remote browsers connect to `/relay/{remote_name}/browser` and receive `{type:"hello",sid}`.

1. Browser sends `{type:"auth.start",a}`.
2. Device replies `{type:"auth.challenge",salt,b}`.
3. Browser sends `{type:"auth.proof",proof}`.
4. Device verifies the SRP proof and replies `{type:"auth.ok",proof,expiresIn:86400}`.
5. Browser verifies the device's proof before accepting a session.

`protocol/auth` implements this exchange with the SRP library, not JavaScript BigInt reimplementations. Invalid public values are rejected. Challenges expire after 30 seconds. At most eight device authentication states/sessions exist. At most five outstanding or failed authentication starts per minute are accepted device-wide; reboot resets this volatile limiter. Successful login grants sensitive-operation access for five minutes, and ordinary access for 24 hours. Reconnect to elevate again. Changing the password/name/cloud enablement or revoking sessions invalidates all authenticated sessions. Disconnecting the relay removes only remote sessions.

Application frames are `{type:"rpc",seq,data}`. `data` is hex AES-256-GCM ciphertext including its tag. Directional keys are HKDF-SHA256 of the SRP session key, with the session ID as salt and UTF-8 info `drouter-request-v1` or `drouter-response-v1`. Nonce: four zero bytes followed by the eight-byte big-endian sequence number. Associated data: UTF-8 `{sid}:{seq}`. Each direction starts at sequence 1; the device accepts only the next sequence and rejects replay. Reauthentication creates a fresh SRP secret and session ID. Responses correlate the decrypted request ID. The client serializes operations. The relay cannot forge valid application packets or read configuration updates.

Browser AES-GCM/HKDF use the maintained Noble implementations, allowing the local UI to work over HTTP on private LAN addresses where WebCrypto is unavailable. WASM randomness uses the browser CSPRNG. Remote access requires HTTPS/WSS; simulator loopback HTTP/WS is explicitly permitted for development. Initial provisioning trusts the physically disclosed WPA2 AP password; use a trusted LAN if provisioning over Ethernet.

## Device ownership and relay envelopes

Remote names are ordinary 3–32 character lowercase ASCII names with digits and single hyphens. The immutable device ID is the full SHA-256 hex digest of its Ed25519 public key. Its first 16 bytes remain the existing public SRP salt fingerprint, so migration and renaming preserve password verification.

A device connects to `/relay/{device_id}/device`. The relay sends a fresh random `{type:"challenge",nonce}`. The device returns `{type:"register",deviceId,name,publicKey,signature}`. Ed25519 signs UTF-8 `drouter-register-v2\n{deviceId}\n{name}\n{nonce}`. The relay verifies the ID/key relationship and signature before requesting a reservation from the internal registry. The challenge is accepted once and expires in 30 seconds. Duplicate live identities are rejected. Names resolve through the registry to relay objects keyed by immutable ID.

`DeviceRegistry` uses SQLite tables `devices(device_id,name,public_key,registered_at,renamed_at,last_connected)` and `names(name,device_id,reserved_at)`. A synchronous transaction enforces unique name ownership and stable public keys. Previous names remain reserved aliases after a signed rename. Connection timestamps update at most hourly. There are no passwords, verifiers, sessions, user settings, or routing payloads in these tables. Internal lookup/reserve endpoints are accessible only through the Worker binding, not external URLs. The additive `v2-registry` migration preserves the relay class and creates the registry class.

Recovery uses the original private identity, exported only by an elevated local operation. Import requires elevated local access, a new password, and revision check; it recreates the verifier on-device and revokes sessions. Losing that key means losing the reserved name. Factory reset cannot authorize a new key to claim it.

The relay sends device frames as `{type:"forward",sid,frame}` and receives `{type:"reply",sid,frame}`. A verified device socket has no daily forced expiration. Browser sessions use the device-advertised expiry, capped at 24 hours (older firmware without an expiry field defaults to 30 minutes). A device disconnect closes its remote browser sessions and clears live data in the UI. Browser disconnect produces `{type:"leave",sid}`. The Durable Object does not store application payloads. Hibernation attachments contain only roles, transient challenges, session IDs, expirations, rate counters and pending deadlines. The live relay uses only cleanup alarms; persistent names live exclusively in the separate registry.

## Limits and failures

- 32 KiB WebSocket/HTTP message maximum; encrypted payload maximum 15,000 bytes; response plaintext maximum 14,000 bytes.
- At most 12 relay sockets, eight browser/candidate sockets from one IP, one pending request per browser, 120 browser frames/minute, 600 device frames/minute.
- Relay request deadline 15 seconds. Browser deadline 17 seconds. BirdDog request timeout two seconds; device operations stop issuing requests after ten seconds. Oversized responses return a structured capacity error instead of truncating state.
- 16 receivers, 64 distinct sources, 16 presets, Wi-Fi profiles bounded by the shared 24 KiB serialized configuration and 13,000-byte redacted-list budgets.
- Routes are successful only after reading the requested source back from the receiver. Presets return one success/failure entry per stored output. A failure can leave a partially applied matrix; there is no fictitious transaction across receivers.
- Routing readback after boot always reflects receivers. Neither boot nor Cloud reconnection applies an old preset.

## Trust boundary

SRP authenticates password knowledge; device registration authenticates ownership of the public name. TLS authenticates the deployed relay. Like every browser application, the remotely served JavaScript must be trusted: an operator able to replace that JavaScript could alter password handling. No independently audited application security claim is made. Production should use reviewed builds and an appropriate CSP. The LAN interface is designed for trusted production/control networks, not arbitrary public HTTP exposure.

## Modification 3 access control and configuration

The version-1 request envelope remains compatible; the local configuration schema is now 3. The generated schema includes saved-source, Simple Mode, Event Mode and authentication/session operations. Source and Simple Mode configuration mutations and Event Mode changes require `confirmed:true` and the current `expected_revision`. Frontends stage edits and display the exact change before sending either field. A cancelled dialog sends no mutation. Ordinary administrator `route.set` and restricted `simple.action.execute` execute immediately without confirmation.

Sessions carry either `admin` or `simple_mode` with a profile ID. Before authenticating, clients send `auth.start` with `multi:true`. The ESP32 returns an administrator challenge plus anonymous SRP challenges for enabled profiles, with no profile names or IDs. The browser computes a proof for each challenge with the entered password; the ESP32 alone selects the matching credential and assigns the role. The same SRP private ephemeral is used for these independently salted challenges; the browser validates the selected server proof before deriving its encryption key. Legacy single-administrator SRP clients remain supported. `auth.login` and `auth.session` return the role only inside an authenticated encrypted session. `auth.logout` removes that session after returning its encrypted acknowledgement.

Each credential uses PBKDF2-HMAC-SHA256 with 100,000 iterations and a 32-byte salt, followed by the established SRP-6a verifier. New Simple Mode credentials and changed administrator credentials use independently random salts. Legacy administrator credentials retain their original identity-derived salt until changed. Duplicate passwords are checked on the ESP32 against each existing salt; neither the password nor a reusable unsalted lookup digest is stored. An administrator password cannot match a profile password, including disabled profiles.

Passwords accept **4–128 Unicode scalar values**, counted by Rust `str::chars()` and browser `Array.from()`. Encoding is UTF-8; there is no Unicode normalization. Combining marks count separately, and a supplementary-plane character counts once. Thus `😀😀😀` is too short and `😀😀😀😀` is accepted. This rule applies to setup, recovery, administrator changes, and Simple Mode passwords. Wi-Fi passwords continue to follow WPA2 byte-length requirements.

**Four-character passwords are weak.** Use longer passwords wherever possible. Online restrictions include at most five outstanding or failed starts per rolling minute, a device-wide failed-proof backoff of 2, 4, 8… seconds capped at 900 seconds, at most eight pending authentication states/sessions, 30-second challenges, 24-hour sessions, 180 encrypted requests per session per minute, existing relay/IP limits, and a shared two-second repeat guard per profile/button across local and remote sessions. Successful authentication releases its start budget but does not reset failed-proof backoff. Rate limits are volatile and reset on physical restart. These controls reduce online guessing; they cannot turn a four-character secret into a strong password or prevent offline guessing after device compromise.

Only `auth.session`, `auth.login`, `auth.logout`, `event.status`, `simple.actions.list`, and `simple.action.execute` are available to restricted sessions. The firmware checks the profile's enabled status on every operation. Changing a profile password revokes its existing sessions; administrator password recovery also rejects passwords already assigned to a profile. Execute accepts only `{id: buttonId}`; unknown fields, foreign buttons, missing outputs and unavailable sources are rejected. The client cannot supply a target override. The stored action is a single fixed receiver/source mapping; action records can later be extended to multiple mappings through a protocol migration.

Event Mode is persisted in the encrypted local configuration. Restricted logins may authenticate to a locked screen, but execution is denied while the flag is set. The existing device mutex covers both Event Mode commits and complete BirdDog switch/readback operations. A switch already executing finishes before activation commits; after activation succeeds, subsequent restricted commands cannot execute. Administrator routing remains available. Disabling Event Mode changes no routing or profile definitions. A missing Event Mode field defaults to locked. A damaged storage slot forces the recovered configuration into locked mode; no valid slot means recovery rather than automatic setup. A RAM ring stores the last 32 access-control configuration events; it is not sent to Cloudflare.

Limits are eight profiles, 1–10 buttons per profile, 64 saved sources, the existing 24 KiB serialized configuration capacity, and 13,000-byte public saved-source/profile lists. Oversized changes fail before flash writes. Discovery availability is persisted only on explicit refresh or source save, avoiding periodic flash writes. The browser also displays current discovery availability. Saved aliases never change NDI network names. Language/appearance preferences stay in browser localStorage; no source, profile, action or verifier is stored on Cloudflare.
